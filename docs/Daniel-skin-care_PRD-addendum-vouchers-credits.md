## 2. מודל נתונים

### 2.1 אוסף חדש `credits` — `users/{uid}/credits/{id}`

| שדה | סוג | משמעות |
|---|---|---|
| `clientId`, `clientName` | string | הלקוחה שהיתרה בחשבונה (המקבלת בשובר) |
| `amount` | number | הסכום המקורי |
| `remaining` | number | היתרה הנוכחית (0 ≤ remaining ≤ amount) |
| `source` | `"voucher"` \| `"refund"` | שובר מתנה או זיכוי רגיל |
| `giftFromClientId`, `giftFromName` | string \| null | הקונה (בשובר בלבד; `null` אם קונה מזדמנת) |
| `voucherId`, `voucherName` | string \| null | הגדרת השובר שממנה נרכש (`null` בסכום חופשי) |
| `expiryDate` | `"YYYY-MM-DD"` \| null | תוקף. `null` = ללא תוקף (ברירת מחדל) |
| `incomeId` | string \| null | ההכנסה של הקונה (בשובר בלבד) |
| `reason` | string | סיבה (בזיכוי רגיל) |
| `status` | `"active"` \| `"used"` | נשמר. `"פקע"` הוא ערך **נגזר** בלבד, כמו בחבילות |
| `voucherSentEmail`, `voucherSentWhatsapp` | boolean | סימון שליחה |

### 2.2 אוסף חדש `vouchers` — הגדרות שוברים

| שדה | משמעות |
|---|---|
| `name` | שם השובר (למשל "שובר ₪300") |
| `amount` | סכום (≥ 0, נעצר ב-0) |
| `expiryDate` | תוקף אופציונלי, `null` כברירת מחדל |

מחיקת הגדרה **אינה** משפיעה על שוברים שכבר נרכשו.

### 2.3 שינויים בישויות קיימות

| ישות | שינוי |
|---|---|
| `income` | `source:"voucher"` חדש. נכתב עם `clientId` של **הקונה** (או `null` לקונה מזדמנת), `creditId`, `treatmentName: "שובר מתנה"` (או שם ההגדרה). בהכנסה מתור/סדרה/מוצר עם קיזוז: שדה `creditApplied` (מספר) |
| `appointments` | `creditApplied` (number, כשיש קיזוז) ו-`chargedFromCredit` (boolean, `true` רק כשהקיזוז כיסה את כל הסכום ולא נוצרה הכנסה) |
| `settings/invitation` | שדות חדשים `voucherSubject`, `voucherBody`. אין מיגרציה |
| `auditLog` | פעולות חדשות בסעיף 9 |

**אין שינוי נדרש ב-`firestore.rules`** (אותו דפוס `users/{uid}/{document=**}`) ואין שינוי ב-`localStore.js`, כי כל האוספים גנריים.

## 6. יתרה בכרטיסיית לקוחה וזיכוי רגיל

| מזהה | דרישה |
|---|---|
| **C-1** | בטאב **"פרטי לקוחה"**, בסוף הטאב (אחרי "לקוחות שהופנו ע״י לקוחה זו" ולפני שורת הפעולות "שליחה לארכיון / עריכה") מוצג תמיד כרטיס **"יתרת זיכוי"**, גם ביתרה 0: סה"כ יתרה זמינה, רשימת היתרות וכפתור "+ הוספת זיכוי" |
| **C-2** | כל יתרה מציגה: סוג ("מתנה מ-X" / "זיכוי"), `remaining/amount`, תוקף (אם יש), תגית סטטוס (פעיל / נוצל / פקע) |
| **C-3** | **סה"כ יתרה זמינה** = סכום `remaining` של יתרות עם `status:"active"`, `remaining > 0` ושטרם פג תוקפן (`expiryDate >= היום`, אותה בדיקה כמו בחבילות) |
| **C-4** | כל הסכומים באזור הזה מסומנים `.sensitive` (מצב קליניקה) |
| **C-5** | כפתור **"הוספת זיכוי"**: סכום (≥0), סיבה (טקסט חופשי), תוקף אופציונלי (ברירת מחדל ריק). יוצר `credits` עם `source:"refund"`, **ללא הכנסה** |
| **C-6** | **עריכה ומחיקה** של יתרה (CRUD): עריכת `remaining`, `expiryDate`, `status`. מחיקה עם אישור ו-Undo. מחיקת יתרה אינה פוגעת בהכנסה של הקונה |
| **C-7** | רישום בלוג: `credit_create`, `credit_edit`, `credit_delete` |
| **C-8** | כל פעולה עטופה ב-try/catch ובהודעת שגיאה (§4.7.1) |

## 7. קיזוז יתרה

### 7.1 כללי הקיזוז (חלים על שלושת המסכים)

| מזהה | דרישה |
|---|---|
| **O-1** | הקיזוז מוצע רק כשלקוחה בעלת `clientId` ויש לה יתרה זמינה (C-3). **לקוחה מזדמנת: אין קיזוז** |
| **O-2** | שדה "קיזוז מיתרה": סכום לעריכה. ברירת מחדל = הנמוך מבין היתרה הזמינה לבין הסכום לתשלום. טווח: 0 עד הנמוך מביניהם (`min="0"`, נעצר ב-0 ובתקרה) |
| **O-3** | **הקצאה בין כמה יתרות:** קודם זו שפגה קודם (יתרה בלי תוקף אחרונה), ובשוויון הוותיקה ביותר (`createdAt`). לוגיקה טהורה אחת ב-`utils/credits.js` (`allocateCredit`), בשימוש בכל שלושת המסכים |
| **O-4** | יתרה שפג תוקפה **אינה** ניתנת לקיזוז |
| **O-5** | **ההכנסה נרשמת רק על החלק ששולם בפועל:** `amount = סכום − קיזוז`. השובר כבר נספר כהכנסה אצל הקונה ולכן אין כפל ספירה. כשיש קיזוז נשמר `creditApplied` על ההכנסה |
| **O-6** | כשהקיזוז מכסה את **כל** הסכום: **נוצרת הכנסה בסכום 0 עם `paid:true`** וללא אמצעי תשלום (סטייה מכוונת מהמפרט המקורי, ראו סעיף 13). אמצעי תשלום אינו נדרש (כפתור האישור לא ננעל בגללו). כך מחיקה, החזרת יתרה ותצוגה פועלות באותו אופן בכל סוגי התשלום |
| **O-7** | כל העדכונים (ירידת `remaining`, מעבר ל-`status:"used"` ב-0, יצירת/דילוג על הכנסה, עדכון התור/החבילה/המלאי) מתבצעים ב-**`batchRepo.commit` אחד**. כשל: הודעת שגיאה ו-`saving` משתחרר |
| **O-8** | אין שינוי בהתנהגות כשהקיזוז הוא 0 |
| **O-9** | עיגול: חישובי קיזוז מעוגלים לשתי ספרות אחרי הנקודה, כדי למנוע שאריות צפות |
| **O-10** | לוג: `credit_apply` לכל יתרה שנוצלה (לפני/אחרי `remaining`) |
| **O-14** | בכל הכנסה שנוצרה עם קיזוז נשמר `creditApplications: [{creditId, amount}]` (בנוסף ל-`creditApplied`), כדי לדעת לאילו יתרות להחזיר |
| **O-15** | **מחיקת הכנסה עם קיזוז** (`Business.jsx`, כל סוג: תור/סדרה/מוצר): אחרי השאלות הייעודיות לסוג, מוצג פופ-אפ "להחזיר ₪X ליתרת הזיכוי?". אישור: `remaining` גדל (עד `amount` המקורי), `status:"active"`, לוג `credit_restore`. יתרה שנמחקה בינתיים: מדלגים בלי שגיאה. הכנסות ישנות בלי `creditApplications`: אין החזרה אוטומטית (תיקון ידני בכרטיס יתרת הזיכוי) |
| **O-16** | **נעילת "שולם" ללא שינוי:** הכנסה בסכום 0 שנוצרה מקיזוז מתנהגת כמו כל תשלום אחר — כדי למחוק אותה יש להסיר קודם את סימון "שולם" |
| **O-17** | בשורת הכנסה עם קיזוז מוצגת תגית "קוזז מיתרה ₪X" (`.sensitive`) |

### 7.2 לפי מסך

## 12. בדיקות QA ידניות

1. **תבניות:** שמירת שני הטאבים; רענון ובדיקה שהערכים נשמרו. מחיקת תוכן השובר ושליחה: צריכה להופיע ברירת המחדל.
2. **₪ בהודעה:** בהודעת שובר של 500 מופיע "500₪" (₪ צמוד אחרי המספר, ללא רווח).
3. **תוקף:** רכישה בלי תוקף: ההודעה כוללת "ללא הגבלת זמן". עם תוקף: תאריך מעוצב.
4. **רכישת שובר:** א׳ קונה ל-ב׳. אצל א׳ מופיעה הכנסה ב"תשלומים נוספים"; אצל ב׳ מופיעה יתרה "מתנה מ-א׳".
5. **מקבלת חדשה:** הוספה מהירה יוצרת כרטיסייה באותו batch. כשל בשמירה לא משאיר לקוחה יתומה.
6. **קונה מזדמנת:** הכנסה עם `clientId:null`, והיתרה נשמרת עם `giftFromClientId:null`.
7. **קיזוז חלקי:** יתרה ₪500, תור ₪300. ההכנסה ₪0 → ראו קיזוז מלא. תור ₪700 עם קיזוז ₪500: הכנסה ₪200, היתרה ₪0 והסטטוס "נוצל".
8. **קיזוז מלא:** תור ₪300 מול יתרה ₪500: אין הכנסה חדשה, היתרה ₪200, התור "שולם" ביומן ובכרטיסייה (D-1, D-2), ואין חובה לבחור אמצעי תשלום.
9. **שתי יתרות:** יתרה עם תוקף קרוב ויתרה בלי תוקף: ננוצלת קודם זו עם התוקף.
10. **יתרה שפגה:** אינה מוצעת לקיזוז, ואינה נספרת בסה"כ.
11. **מסלול חבילה:** תור שחויב מחבילה לא מציג קיזוז ולא משתנה.
12. **סדרה:** רכישה מקוזזת חלקית: הכנסה על ההפרש. מקוזזת מלא: חבילה עם `incomeId:null` ללא קריסה.
13. **מוצר:** מכירה ללקוחה מזדמנת: אין קיזוז. מכירה ללקוחה עם יתרה: קיזוז והמלאי יורד.
14. **מחיקת הכנסת שובר:** חלה אזהרה כשהיתרה נוצלה, והצעה למחוק גם את היתרה (D-3).
15. **כשל באמצע:** ניתוק רשת לפני אישור: הודעת שגיאה, `saving` משתחרר, והיתרה לא ירדה.
16. **מצב קליניקה:** סכומי היתרה מטושטשים.
17. **ערכים שליליים:** הקלדת "-" בסכום שובר, זיכוי וקיזוז: נשמר 0.
18. **גיבוי:** "גיבוי עכשיו" יוצר גיליון "זיכויים". עריכת יתרה מפעילה גיבוי חכם בריצה הבאה.
19. **מסך הבית:** שישה כפתורים, וניווט תקין לכל אחד.

## 13. סטיות מכוונות ומגבלות ידועות

**מגבלות שהתקבלו:**
- סדרה ששולמה כולה מיתרה מקבלת הכנסה בסכום 0, ולכן ב"סיכום לפי מוצר" החלק המשוער מהחבילה עבורה הוא 0 (`packageAttributedByTreatment` מחלק את סכום ההכנסה).
- מחיקת הכנסה עם קיזוז מציעה להחזיר את היתרה (O-15). תורים/סדרות שנסגרו בבדיקות **לפני** התוספת (בלי הכנסה ובלי `creditApplications`) לא נתמכים אוטומטית: מחיקה והחזרת יתרה ידניים (עריכת היתרה בכרטיסיית הלקוחה, C-6).
- מחיקה סופית של לקוחה אינה מוחקת את יתרותיה (עקבי עם חבילות).
- אין התראת "יתרה עומדת לפוג" בדשבורד (מחוץ לסקופ, אפשר להוסיף כמו `expiringPackages`).
- הסכומים מעוגלים לשתי ספרות (O-9).

**סטיות מכוונות שהוחלטו במהלך המימוש:**
1. **כיסוי מלא מיתרה (תור, סדרה ומוצר):** נוצרת הכנסה בסכום 0 עם `paid:true` ו-`paymentMethod:""`, במקום "ללא הכנסה" (O-6/O-11/O-12/O-13). נימוק: בלי רשומת הכנסה אי אפשר היה למחוק תור ששולם מיתרה, ומכירות מוצר לא הופיעו ב"מכירות"/"מוצרים" של הלקוחה. נמצא בבדיקות; הוחלט להחיל בכל שלושת המסכים. **נעילת "שולם" נשארת** (O-16).
2. `useAutoBackup.js` נוסף לרשימת הקבצים המשתנים: הוא חייב להירשם ל-`credits` כדי שהגיבוי החכם יזהה שינויים (השלמה ל-D-5).
3. הכנסת שובר שומרת גם `giftToClientId`/`giftToName` (להצגה ב"תשלומים נוספים").
4. מיקום "יתרת זיכוי" הועבר מטאב "רשימת תורים" לטאב "פרטי לקוחה", בסוף הטאב (בקשת המשתמשת). הכרטיס מוצג תמיד, גם ביתרה 0.
5. כשל בכתיבת לוג אחרי פעולה שהצליחה נבלע (נרשם ל-console) ואינו מציג "הפעולה נכשלה".

**נושא פתוח:**
- האם לאפשר שובר ללא תוקף כברירת מחדל גם בהגדרה (כרגע כן: ריק = ללא תוקף).

**חוק שאלה:** כל סטייה ממפרט זה במהלך המימוש חייבת להירשם כאן עם נימוק, כמו בתוספות הקודמות.
